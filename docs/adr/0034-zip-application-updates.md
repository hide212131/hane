# ADR-0034: ZIP配布を継続したアプリ本体の更新

日付: 2026-10-17
状態: Accepted（PR #509で採用）。実装の進捗は[Issue #510](https://github.com/hide212131/hane/issues/510)に従う。WindowsとmacOSの実配布物での二版更新・復旧とU-01〜U-15の証拠がそろうまで、#510は完了扱いにしない。
調査基準: `e82b9a9fe42280bfa78497746bcd7e21c73430c5`（設計時点のSHAであり、current mainではない）

要求・受入条件の正本: [Issue #508](https://github.com/hide212131/hane/issues/508)

## 背景

HaneはmacOS arm64の`Hane.app`とWindows x64のポータブル版をGitHub ReleasesのZIPとして配布している。利用者は設定画面の「最新に更新する」から、ZIPの手動展開を繰り返さずアプリ本体を更新したい。

Windowsでは任意の展開先に利用者ファイルが混在でき、Explorer拡張も同梱する。macOSではアプリの配置場所・署名・Gatekeeperの制約がある。ダウンロードするだけでなく、文書を失わない再起動、真正な配布物の選択、プロセス終了後の置換、失敗・中断からの復旧が必要である。

## 決定

1. ZIP配布と現在のOS/CPU対応を維持する。初期対象は`aarch64-apple-darwin`と`x86_64-pc-windows-msvc`のstable releaseとし、利用者の明示操作で確認・取得し、別操作の「再起動して更新」で適用する。
2. GitHub Releasesを発見・配信に使い、アプリに埋め込んだ公開鍵による署名済みカタログとZIP全体のSHA-256で取得物を検証する。公開GitHub APIの認証情報を要求しない。APIの`digest`や同梱証明書だけを更新の信頼の根にしない。
3. 更新用の独立したRust libraryとhelperを設ける。アプリが確認・取得・編集状態の調停を担当し、現在インストール済みの信頼できるhelperのコピーが、親の終了後にローカルの検証済み候補を適用する。helperはネットワーク取得、文書保存、権限昇格、任意コマンド実行をしない。
4. Windowsは署名された所有ファイル一覧に限定した置換を行う。展開先フォルダ全体を入れ替えない。Explorer DLLをバージョン別のパスへ変更し、使用中の旧DLLを残して更新する。
5. macOSは同じBundle IDと固定したDeveloper ID Team IDの署名・notarizationを検証した`.app`を、対応するローカルファイルシステム上で原子的に交換する。署名・notarizationを整えるまで、macOSの自動適用を有効にしない。ZIPの形式変更だけで署名問題を解決したとは扱わない。
6. 未保存文書、未保存設定、保存・rename・AI処理等の未確定操作があれば再起動を保留する。通常終了の既存draft flushを、更新の保存成功の証拠として流用しない。更新用の確認可能な永続化境界を設ける。
7. 再起動中はインストール単位で起動を調停し、新版が永続データを書き始める前の限定した起動確認でcommitする。それ以前の失敗では旧版へ戻す。commit後の任意の製品不具合まで、自動rollbackの保証には含めない。
8. アプリ本体更新とHane専用Codex runtime更新を別の所有者・保存先・署名ドメインにする。AIのログイン・秘密・runtime・Skillsを本体更新の置換対象にしない。

具体的な状態、ファイル形式、OS処理、故障時の動作は[実装仕様](../application-update-implementation-spec.md)、実装単位と受入条件は[引き継ぎ](../application-update-implementation-handoff.md)を正とする。

## 代替案

| 案 | 判断 |
|---|---|
| 設定からReleaseページを開くだけ | 自動適用できない場合の代替操作として残す。要求するアプリ本体更新の完成形にはしない。 |
| WindowsをMSI/MSIX全体配布、macOSをPKGへ先に移行 | インストールの統一には利点があるが、ポータブル配布を変える。今回の機能の必須条件にしない。既存のMSIXはExplorer用のsparse packageであり、本体更新を管理していない。 |
| `self_update`等で実行ファイルだけを交換 | `.app`、Explorer DLL、複数ファイルの整合、文書と再起動の調停まで満たせないため、単体バイナリ交換を完成形として採らない。 |
| SparkleとWinSparkleをOSごとに導入 | 配布・署名・更新処理を実績ある基盤へ委ねられる一方、今回必要なWindowsポータブル一式と独自shell配置、共通の保存境界を別途設計する必要がある。v1は共通の署名契約と小さいOS adapterで進める。独自helperのOS試験を維持できない場合はこの判断を再検討し、安易に未検証の置換へ簡略化しない。 |
| AI runtimeのinstallerをそのまま本体更新に拡張 | 導入対象・起動責任・終了条件が異なる。AI serviceへの本体更新依存や、固定版runtime取得を動的な本体カタログに流用することを避ける。 |

## 制約と影響

- 更新機能を持たない既存版からは、一度だけ更新対応ZIPを手動導入する。初回から既存バイナリを遠隔で更新できるとはしない。
- 書込不能・共有/ネットワークドライブ・移動中の配置・未対応CPU・開発ビルド・署名未準備などには、理由と手動ダウンロードの導線を表示する。一般の編集機能は使える。
- 署名鍵の発行・保管、macOSのDeveloper IDとnotarization、配布workflowの改訂はリリース有効化の実作業であり、本ADRの保存で完了しない。
- 配布workflow等の保護パス変更は、明示した配布基盤専用PRで行う。製品workerの保護制限を緩めない。
- 既存データ形式を旧版が読めなくなる更新はv1の自動適用から除外する。将来それを可能にする場合は、データ移行とrollback方針を別途改訂する。
- 独自のhelper、復旧journal、起動調停を保守する費用を受け入れる。通常の本文編集・描画経路にネットワーク確認やZIP解析を追加しない。

## 適用状態

このPRは文書のみ。公開鍵や証明書、helper、画面、配布metadataはまだ追加していない。設計PRのmergeは設計の保存であり、更新機能の出荷・安全性検証・関連Issueの完了ではない。ADR-0033は別の設計PR #484が使用しているため、本件は0034を使う。
