# ADR-0001: Phase 0 技術検証方針

## ステータス

承認済み

## 日付

2026-08-24

## 背景

本プロジェクトは、Rust と GPUI を使って、ネイティブで高速な WYSIWYG Markdown エディタを開発する。

製品の目的は機能数を増やすことではない。起動直後に編集でき、巨大な Markdown ファイルでも入力が引っ掛からないことを最優先する。

RFP では、以下を設計上の前提としている。

- Markdown ソースを唯一の正とする。
- Electron、Chromium、WebView、DOM、HTML/CSS、Monaco、CodeMirror、ProseMirror を本文編集・描画の基盤にしない。
- キー入力と IME 入力は、Markdown 解析、画像読み込み、保存、シンタックスハイライト、全文レイアウトを待たずに即時反映する。
- 10 MB および 100 MB の Markdown 文書で性能を測定する。
- 日本語 IME 対応を初期段階から必須とする。
- 第1段階は macOS / Apple Silicon を基準にしつつ、エディタ中核へ不要な OS 固有処理を持ち込まない。

完成品の開発から始めると、入力遅延、IME、巨大バッファ、描画方式に関する最重要リスクが、過剰な製品コードの中に埋もれる。

そのため Phase 0 では、製品版ではなく小さな技術検証アプリを作り、コア編集ループが成立するかを先に測定する。

## 決定

Phase 0 は製品版の最初の実装ではなく、技術検証用プロトタイプとする。

Phase 0 で実装する範囲は以下に限定する。

- GPUI アプリケーションウィンドウ。
- 1つの巨大な編集可能 Text Buffer。
- カーソル移動。
- 日本語 IME の未確定入力と確定入力。
- 太字だけの最小限の Markdown 風表示。
- 縦スクロール。
- 起動、入力遅延、解析、レイアウト、描画、スクロール、メモリ使用量の計測。

Phase 0 では以下を意図的に作らない。

- Markdown 全機能。
- 完全な WYSIWYG の Source ↔ Visual 位置変換。
- ファイルツリー、ワークスペース管理、プラグイン、AI、Git、ターミナル、設定、テーマ。
- 完成品としてのアプリケーションシェル。
- ブラウザベースの編集・描画レイヤー。

Phase 0 の目的は、GPUI を使った本文編集方式が 10 MB / 100 MB 文書でも入力応答性を維持できるかを確認することである。

Phase 0 では以下の設計規則を固定する。

1. ユーザー入力は、入力処理経路上で同期的に Document Buffer へ反映する。
2. 重い処理は入力処理経路から外す。
3. バックグラウンド処理の結果には文書 revision と対象範囲を付与し、古い結果は ADR-0005 の規則に従って破棄または非重複範囲へ部分適用する。
4. 通常の編集で、単一の巨大な Rust `String` を毎回コピーする構造にしない。
5. レイアウトと描画は、可視領域と小さな overscan 範囲に限定する。
6. バックグラウンドの表示更新が発生しても、IME composition 状態を破壊しない。
7. 性能は主観的な手触りではなく、自動化または再現可能な手順で測定する。

Phase 0 では、RFP が後続フェーズでの置き換えを許容する箇所について、暫定的な内部構造を使ってよい。

ただし、入力処理経路に現れる構造は、実際の遅延リスクを隠さない程度に本番想定へ近いものにする。

## 合格条件

Phase 0 の完了時には、少なくとも以下を測定した短いレポートを作成する。

- Warm start time。
- Cold start time。
- Keystroke-to-frame latency。
- Keystroke-to-model latency。
- スクロール中の frame time。
- 太字表示実験における parse / presentation update time。
- Layout time。
- Memory usage。

テスト文書には少なくとも以下を含める。

- 10 MB の Markdown 風文書。
- 100 MB の Markdown 風文書。
- 多数の小さな段落を持つ文書。
- 日本語テキスト。
- ASCII、日本語、絵文字、結合文字、サロゲートペア相当の Unicode scalar value を含む混在テキスト。

Phase 1 へ進む目安は以下とする。

| 指標 | 目標 |
|---|---:|
| Warm start 中央値 | <= 150 ms |
| Cold start 中央値 | <= 400 ms |
| 通常文書 keystroke-to-frame p95 | <= 8 ms |
| 通常文書 keystroke-to-frame p99 | <= 16 ms |
| 100 MB 文書 keystroke-to-frame p95 | <= 16 ms |
| 100 MB 文書 keystroke-to-frame p99 | <= 33 ms |
| スクロール中の安定フレームレート | >= 60 fps |
| 空文書・起動直後のメモリ使用量 | <= 60 MB |
| 10 MB 文書のメモリ使用量 | <= 120 MB |
| 100 MB 文書のメモリ使用量 | <= 350 MB |

これらの値を満たせない場合でも、ボトルネックが特定され、Phase 1 前に必要な構造変更が明確になれば、Phase 0 は有効な成果とみなす。

## 結果

この決定により、製品機能の実装より先に、性能、IME、巨大文書編集、GPUI 描画方式のリスクを検証する。

初期段階では、見た目の完成度や機能数よりも、計測基盤、Text Buffer、入力処理、スクロール、可視領域描画を優先する。

利点は、Phase 1 へ進む前にコア編集ループの実現性を根拠付きで判断できることである。

欠点は、Phase 0 の成果物が利用者向けのエディタとしては不完全に見えることである。

Phase 0 で GPUI、文字レイアウト、IME、Text Buffer、仮想スクロールのいずれかに重大な制約が見つかった場合は、製品実装へ進む前にアーキテクチャを変更する。

## 検討した代替案

### 最初から完全な WYSIWYG エディタを作る

Phase 0 では採用しない。

入力遅延、日本語 IME、巨大バッファ、描画方式の検証前に実装量が増えすぎ、問題の切り分けが難しくなるため。

### Web ベースのエディタでプロトタイプを作る

採用しない。

RFP はブラウザベースの本文編集・描画基盤を明確に禁止している。WebView や DOM を使ったプロトタイプでは、本製品が採用するアーキテクチャを検証できない。

### Phase 0 をプレーンテキストのみにする

不十分なため採用しない。

プレーンテキスト編集は必要だが、WYSIWYG Markdown エディタに必要な presentation 更新や invalidation のリスクを検証できない。Phase 0 では、全 Markdown 対応ではなく、太字だけの最小限の表示実験を含める。

### Phase 0 で Markdown パーサ統合まで完成させる

採用しない。

全文 Markdown 統合は、入力処理、Text Buffer、IME、可視領域描画が測定できた後に扱う。Phase 0 では、遅延と invalidation のリスクを確認できる最小限の presentation に留める。

## 後続 ADR

Phase 0 の結果をもとに、少なくとも以下の ADR を作成する。

- Text Buffer のデータ構造選定。
- Source offset、Visual offset、Cursor mapping のモデル。
- バックグラウンド解析と revision 管理。
- GPUI レイアウトと可変高さ仮想スクロール。
- IME composition モデル。
- Performance Harness の測定方式。
- 配布前の依存関係とライセンス確認。
