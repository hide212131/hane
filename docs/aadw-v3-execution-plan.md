# AADW v3 実装・評価・移行計画

## 適用範囲

設計Issue [#332](https://github.com/hide212131/hane/issues/332)の成果物。実装は[#333](https://github.com/hide212131/hane/issues/333)で追跡する。[ADR-0031](adr/0031-aadw-v3-jev-bounded-execution.md)と[v3設計書](agentic-development-workflow-v3.md)を参照する。

文書のmergeでは稼働を切り替えない。実装の進捗はIssue/PRと実行の証拠で確認し、この文書のチェックリストを別の現在状態DBにはしない。[Commander Policy](aadw-command-policy.md)が現行運用の正本である。

## 1. V3-1: 指定したCodexで一回の作業を実行する

最初はJevの判断を適用せず、独立した開発用実行器で一回の実装と検証を行う。実装言語、配置、固定バージョンは既存の開発運用構成を読んで実装担当が決める。App Serverを用いるローカル試行から始め、CIやHane製品への統合は混ぜない。

受け入れ証拠として、指定モデル・推論量、実際のrequest/event、終了状態、候補内容と差分、検証command/exit code/log、利用量を残す。モデルが使えない場合と中断時に、黙った代替や重複実行をしないことも確認する。

この段階の成功は、自動的な次工程判断が動いたことを意味しない。

## 2. V3-2: Jevの回答を取得し検査する

Choiceによる初期選択と、Noulによる独立した受入条件の裏付け等を接続する。実行器はschema、必要な回答、候補集合、有限で範囲内の数値、入力の鮮度を検査する。確率分布に整合検査を行う場合はSDK仕様と丸めの許容範囲を明示し、独自に数値を書き換えない。

fixtureによる契約試験を先行させ、許可された環境で実API応答も確認する。fixture成功と実推論の正しさを混同しない。同じリクエストの回答に依存する質問を含めず、必要な証拠の追加取得を挟む場合だけ再問い合わせする。

APIキーをworkerや検証プロセスへ渡さないこと、デバッグログへ本文や秘密情報を不用意に出さないことを確認する。通信の再試行にはSDK既定値を含めて総上限を設け、実装の再試行とは別に集計する。

## 3. V3-3: 判断を適用せず比較する

Jevの提案を記録するが、自動で修正・切替・完了へ進めない観測運用で評価する。Commanderが従来どおり実行判断を行い、観測結果との差を確認する。

比較対象は、現行経路、Luna単独、Luna+Jevとする。費用改善をLunaの変更効果とJevの追加効果に分ける。同じ課題・初期コミット・検証条件・予算を可能な範囲でそろえ、前の試行の修正を次の条件へ持ち込まない。揃わない環境差は記録する。

成功例だけでなく、証拠不足、影響範囲の拡大、古い差分、入力への命令混入、同じ失敗の反復を含める。質問別の誤判定、誤完了、無駄な切替、呼出数、全試行の費用・時間を記録する。少数例の割合を一般的な精度保証として扱わない。

閾値、許可モデル、総実装回数、経過時間、通信再試行、利用量の上限はこの評価を根拠に決める。設定が空なら自動判断を適用しない。記事の閾値や料金をそのまま採用しない。

## 4. V3-4: 明示的なPRで限定運用を有効にする

有効化PRには、対象Issue群・変更領域、認証方式、実行器/質問/モデルの版、評価結果、上限、必要な検証、停止と復帰の方法を記載する。

同PRでCommander PolicyとAGENTSを更新し、v2の「毎回Commanderが一つのactionを選ぶ」「通常はClaudeが実装する」と、v3で許可する委譲範囲の関係を明記する。設計文書だけを根拠に既存規定を迂回しない。切替後は判断規則をCommander Policyへ集約し、質問・実行器はその範囲内で動く。

初期の自動化は、許可された一件の調査・実装・検証の反復と、最終受入への提出までとする。自動merge、権限拡大、設計・範囲変更、検証の免除は含めない。保存・undo/redo・入力等は既存の厳しい受入基準を保つ。

## 5. 試験表

| ID | ケース | 合格時に確認できること |
|---|---|---|
| T01 | 許可モデルと推論量で正常実行 | 指定と実行が一致し、差分・検証結果・利用量を取得できる |
| T02 | モデルまたは推論量が利用不可 | 候補外を選ばず、黙った代替や別課金を行わない |
| T03 | テスト成功だが受入条件の証拠がない | COMPLETEせず必要な証拠を取得する |
| T04 | テストの失敗・timeout・未実施・途中中断 | 成功と区別され、最終受入へ偽の成功を渡さない |
| T05 | head変更、必要なbase変更 | 古い判断・証拠を適用せず再観測する |
| T06 | headは同じだが未コミット/未追跡内容が変化 | candidate内容の違いを検出し、古い検証を流用しない |
| T07 | 受入条件または許可設定が応答待ち中に変更 | 古い入力への回答を破棄する |
| T08 | 禁止パス、権限追加、ログ中の誘導命令 | Jevの回答によらず許可範囲を越えず、秘密情報を渡さない |
| T09 | 不正応答、回答欠落、候補外、NaN等 | 判断を採用せず、通信障害と製品失敗を区別する |
| T10 | 429/一時障害/認証失敗 | 上限内の通信再試行と停止を区別し、無限再試行しない |
| T11 | 同じ原因の反復、予算・時間超過 | 次の実装を開始せず、未解決事項と全試行の利用量を返す |
| T12 | 検証中に停止し、再開またはv2へ復帰 | 旧プロセスの終了とcurrent factsを確認し、二重writerにならない |
| T13 | COMPLETEだがreview/GUI/CIが不足 | 実装候補にとどまり、mergeできない |
| T14 | 費用不明、途中失敗、親子usage | unknownをゼロにせず、失敗を除外せず、二重加算しない |

fixtureと実API、ローカル候補と提出head、意味評価と権限検査を区別して証拠を残す。すべての試験で実サービスを呼ぶ必要はないが、実API確認をfixtureだけで代替したと報告しない。

## 6. 停止・再開・v2への復帰

停止時は新しいactionを発行せず、実行中turnと検証プロセスの終了を確認する。未反映patch、候補内容、実行履歴、未解決の検証を保存する。秘密情報は含めない。

再開時はGitHubのcurrent head/baseと実行済み操作を再取得し、古いCOMPLETEや選択結果を再利用しない。v2へ戻す場合も同じbranchに二人のwriterを作らず、既存の未完了差分をCommanderが扱えるように引き渡す。

有効化を取り消す操作は、新しいv3起動を止める最小の設定・Policy変更で行う。既に存在するGitHubのIssue/PR、証拠、費用履歴を消して正常だったことにしない。

## 7. PR分割と今回の非対象

V3-1、V3-2、評価・有効化は別PRに分けられる。同じ責務の修正と検証をまとめ、独立した製品機能や全域リファクタリングは混ぜない。#297全体は待たないが、変更する運用経路の進行中PRとの重なりを確認する。

今回の設計PRはMarkdown文書と案内だけを対象にする。コード、workflow、秘密情報、依存関係、バージョン、既存fallbackは変更しない。GUI validationは不要であり、docs-only差分・参照・current-head review・該当CIを確認する。

実装Issue #333は本設計PRで閉じない。設計Issue #332の完了は文書の受入であり、実API試験やv3の性能・稼働を保証しない。
