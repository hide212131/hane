# AADW v3 実装・評価・移行計画

## 適用範囲と改訂

初版[#332](https://github.com/hide212131/hane/issues/332) / PR #334を[#335](https://github.com/hide212131/hane/issues/335)で改訂する。実装は[#333](https://github.com/hide212131/hane/issues/333)で追跡する。[ADR-0031](adr/0031-aadw-v3-jev-bounded-execution.md)と[v3設計書](agentic-development-workflow-v3.md)を参照する。

起点を「独立したCodex App Server実行器」から「ChatGPTアプリ内Commander→既存GitHub接続→Actions→Claude Code」に変更する。条件付きでCodexへ切り替え、通常レビューをCodeRabbitへ依頼し、アプリからJevを呼んで限定判断を委譲する。

文書mergeでは運用を切り替えない。[Commander Policy](aadw-command-policy.md)が現行判断の正本であり、Claude優先・利用上限時Codex・Codexレビューを維持する。以下の段階番号は今回改訂後の意味で使う。初版V3-1のCodex単独試行を必須の先行作業にしない。

## 1. V3-1: アプリから既存Actionsへ依頼し、結果を読み戻す

アプリ側の手順を整え、current Policy、Issue/PR/head/baseを読む。承認済みのPRコメントで現行Claude workflowへ指示し、依頼コメントとrunの対応、actor・head検査、変更反映、current-head CIを確認する。設定文を置いたことだけで接続済みとしない。

Claudeはコードとテストファイルを編集する既存権限を維持し、テスト実行・pushをworkerへ移さない。通常worker、反映処理、CI/GUIを分ける。利用上限時の既存Codex fallbackはsource run/attemptとcheckpointの照合、旧worker終了、単一writer、実モデル設定を確認する。行き詰まりによる切替はこの経路の失敗分類に混ぜない。

アプリで待機・再開したときにcurrent factsを読み直せること、起動済みjobの重複依頼をしないことを試験する。閉じたアプリが次のactionを自動発行すると仮定しない。Actions→Actionsが必要ならGITHUB_TOKENのissue_comment制約を確認し、許可した認証/起動方式を別途検証する。

成果物は、アプリから使える手順、実際の依頼とrun/結果の証拠、確認できた利用量、未対応の接続条件。独立した司令塔やHane製品の設定画面は作らない。

## 2. V3-2: CodeRabbitへ明示的に依頼し、結果を検証する

CodeRabbit GitHub Appの導入権限、契約・利用枠、対象repo、外部送信・保持条件を確認する。未設定ならこの段階は未完了とする。自動レビュー/自動差分レビューと別の自動起動条件を確認し、原則として明示依頼だけにする。日本語・状態/範囲の表示を確認し、自動修正・生成・CI修正・競合解消を無効化する。App権限自体を読み取り専用と誤認しない。

アプリのGitHub接続から初回full review、修正後incremental reviewを依頼し、実際のactorで受理されることを確認する。Actionsからの配送を採用する場合は別に実証する。対象head、信頼する結果の出所、完了/失敗/省略、対象ファイル、未解決指摘を読み戻す。対象headを特定できないまま成功にしない。

incrementalは新規差分だけなので、現PR全体を裏付けられなければcurrent-head full reviewへ戻す。指摘の原因整理と修正指示はアプリ側で行い、現在の実装担当へ戻す。CodeRabbitの完了とmergeを分ける。接続試験中も現行の必須レビューを勝手に置き換えず、通常担当の移行はV3-4で明示する。

## 3. V3-3: アプリからJevを呼び、判断を比較評価する

アプリで実際に使えるツール/helperからJevを呼ぶ。Choice/Noul、独立質問の合成、schema・候補・有限数値・鮮度の検査を実装し、秘密情報を会話・worker・検証プロセスへ渡さない。fixture試験の後に、許可されたアカウントで実API応答を確認する。SDK/モデル/質問/Policy版を残す。

最初はJevの提案を記録するだけにし、現行Policyに従いCommanderが実行を選ぶ。到達点は参考情報の表示だけではなく、評価できた通常判断をV3-4で委譲することである。Claudeの実装行き詰まりによるCodex切替は、利用上限とは別の条件・証拠・上限で評価する。

比較は、A: 現行経路、B: Claude優先/条件付きCodex＋CodeRabbitでJevなし、C: 同じ実装・レビュー構成＋Jev、とする。BとCでレビュー条件をそろえ、CodeRabbit導入効果とJev追加効果を混同しない。同じ課題・初期head・検証・予算を可能な範囲でそろえ、前条件の修正を次へ持ち込まない。

成功例だけでなく、証拠不足、影響範囲拡大、古い回答、入力への命令混入、CodeRabbit未完了、同じ失敗の反復を含める。誤完了、誤った切替、呼出数、全試行の費用・時間を測る。Commander/レビュー/CIの計測範囲と未取得を明示し、少数例の割合を精度保証としない。

質問別の閾値、許可設定、総実装回数、経過時間、通信再試行、利用量上限を結果から決める。SDKの通信再試行とコード修正を別に数える。設定や必要証拠が空なら自動判断を適用せず、記事の数値をそのまま採用しない。

## 4. V3-4: アプリ中心の限定運用を明示的に有効化する

有効化PRで対象作業・変更領域、アプリの対応機能、実装経路・認証、Jev/CodeRabbitの接続・版・設定、評価結果、上限、必須検証、停止・復帰を明記する。Commander PolicyとAGENTSを同時に更新し、現行のone-action、Claude/Codex条件、Codexレビューとの関係を整理する。

承認済み通常判断だけをJevへ委譲し、アプリ側の手順から実装指示・追加検証・レビュー依頼へ接続する。最終受入・merge、範囲/設計変更、重大問題の免除、権限拡大はCommanderへ残す。CodeRabbitを通常レビューに移行する時点でCodexの自動レビュー設定も確認し、不要な二重レビューを避ける。追加レビューの選択は明示する。

起動済みActionsとCodeRabbitを追跡し、アプリが再開しない間の次action発行を保証しない。無人継続機能は別途評価した場合だけ追加する。保存・undo/redo・入力等の厳しい受入条件は維持する。

## 5. 試験表

| ID | ケース | 合格時に確認できること |
|---|---|---|
| T01 | アプリからClaudeへ依頼 | current Policy/actor/headを確認した依頼が対応するrunを起動し、結果を読み戻せる |
| T02 | Claude利用上限 | source run/attempt・checkpoint・headを照合してCodexへ引き継ぐ。別の失敗を利用上限に偽装しない |
| T03 | 実装の行き詰まり | 失敗と修正の証拠・上限を基に別途承認した条件だけで切り替える |
| T04 | 認証・権限・モデル利用不可 | 別認証・別課金・無断モデル代替で回避しない |
| T05 | workerの作業終了と反映 | テストファイル作成とテスト実行を区別し、隔離・保護パス・単一writerを保つ |
| T06 | CI失敗・timeout・未実施 | 成功と区別し、製品・環境・証拠不足を混同しない |
| T07 | CodeRabbit初回/差分依頼 | 実actorで受理され、結果の出所・対象head・検査範囲を照合できる |
| T08 | CodeRabbit未導入・上限・error・skipped・除外 | 指摘ゼロと誤認せず、必要なレビューは未達とする |
| T09 | incremental結果の範囲不足 | 旧headのpassを継承せず、必要ならcurrent-head full reviewを依頼する |
| T10 | レビュー指摘と自動修正の分離 | 原因をまとめて現在の実装担当へ返し、CodeRabbitには変更させない |
| T11 | head/base/未コミット/未追跡内容が変化 | 旧検証・旧回答を採用せず、必要な範囲だけ再観測する |
| T12 | 受入条件・許可設定が応答待ち中に変化 | 古い入力へのJev回答を破棄する |
| T13 | 禁止パス・権限追加・誘導命令 | 回答によらず許可範囲を越えず、秘密情報を露出しない |
| T14 | 不正JSON・回答欠落・候補外・NaN | 判断を採用せず、モデルの能力不足や成功に変換しない |
| T15 | Jevの429/timeout/認証失敗 | 通信再試行の総上限を守り、必要ならCommanderへ戻す |
| T16 | アプリ終了・再開、切替時の旧job存続 | runと未反映patchを再取得し、全工程の自動継続を装わず、二重writer/依頼を作らない |
| T17 | Actionsからのコメント配送 | GITHUB_TOKENの別Actions起動制約を検出し、実証した認証/起動方法だけを使う |
| T18 | COMPLETEでもCI/review/GUI不足 | 実装候補にとどまり、mergeしない |
| T19 | 同じ原因の反復、予算/時間超過 | 次の試行を止め、未解決事項と失敗を含む利用量を返す |
| T20 | 費用不明、旧head、親子usage | unknownをゼロにせず、失敗を除外せず、二重加算しない |

fixtureと実API、文書検査と実接続、候補内容と提出headを区別する。すべてのケースで実サービスを呼ぶ必要はないが、接続・実推論の確認をfixtureだけで代替したと報告しない。

## 6. 停止・再開・v2への復帰

停止時は新しい依頼を止め、GitHub上のClaude/Codex/CI/レビュー処理の状態を確認する。作業中のworkerを切り替える前に終了を確認し、未反映patch、対象内容、未解決事項を秘密情報なしで残す。アプリを閉じただけではjob停止と扱わない。

再開時はcurrent head/base、run、レビューと実行済み操作を再取得する。過去のCOMPLETEや会話の「次にやること」をそのまま実行しない。v2へ戻す場合も旧workerを止め、同じbranchに二人のwriterを作らない。

復帰は新しいv3依頼・Jev判断適用を止め、通常レビューを含む有効化時の変更を明示的に戻す。Issue/PR、失敗、費用履歴を消して成功扱いにしない。接続の未確認を理由に現行の成功済み検証まで書き換えない。

## 7. v3を誰が実装するか、PR分割、今回の非対象

v3という仕組み自体の実装も、アプリ内Commanderが既存ActionsからClaudeへ依頼できる。通常workerが変更可能な連携コード・テストと、`.github/`・AGENTS・Commander Policy・認証等の保護された運用基盤変更を分ける。後者は明示した権限とレビューを持つ別PRで扱い、通常workerの禁止パスを一括解除しない。

V3-1〜4を必要なPRに分け、既存部品を優先する。#297全体を待たず、変更する運用経路の進行中PRとの重なりだけを確認する。独立した製品機能や大規模な汎用制御基盤を混ぜない。

今回の#335は既存5文書と#333の整合のみ。製品コード、workflow、秘密情報、CodeRabbit設定、依存関係、バージョンは変更しない。GUIは不要とし、文書差分・参照・現行経路のcurrent-head review・該当CIを確認してmergeする。#333は実装・評価・有効化の証拠がそろうまで閉じない。
