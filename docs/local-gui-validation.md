# Local GUI validation 設計

## この文書の位置づけ

2026-09-07 に採用した方針を、実装前の設計として記録する。**この文書の追加は、自動検証が動作済みであることを意味しない。** 非公開リポジトリの作成、Mac の設定、認証情報の登録、ワークフローやマージ条件の変更は、後続の作業で行う。

採用理由と代替案の比較は [ADR-0024](adr/0024-local-gui-validation.md)、エージェントの役割と進行条件は [AI Agent Development Workflow](agentic-development-workflow.md) を正とする。この文書は、その中の Local GUI validator の実行方法を具体化する。Issue [#55](https://github.com/hide212131/hane/issues/55) は進捗・実験結果を追跡し、長い設計説明の正本にはしない。

以下では、既存コード・実験で確認できたことと、今回決める実装方針を分ける。候補のリポジトリ名、未実装のコマンド名、状態の保存形式は、存在する機能として扱わない。

## 1. 何を成立させるか

GitHub の Issue や Pull Request のコメントから Claude Code が実装・修正した後、対象コミットの Hane をログイン済みの Mac で検証し、合否と証拠を Pull Request に返す。

```text
Issue / PR comment
    -> Claude Code が実装・修正
    -> 対象 head SHA の CI とレビュー
    -> 既存の進行条件と GUI requirement classification を確認
    -> 非公開の制御用リポジトリへ検証を依頼
    -> ローカル Mac で Hane 専用の検証を実行
    -> GitHub 側で対象 SHA・実行世代・結果を照合
    -> PR に結果を報告
    -> Copilot final judge / 既存のマージ条件の検査
```

自動検証は Computer Use のセッションやアプリ承認に依存させない。事前に決めた操作と合否確認を行う検証コマンドを主経路とし、AI による画面の確認は必要に応じて後段に分ける。

Claude が実装し、Codex がレビューし、Copilot が次の処理を判断する役割分担は変更しない。検証側はコードを修正しない。最終判断やマージを Mac に任せない。

### 今回の対象外

任意の外部 Pull Request を個人用 Mac で無人実行すること、汎用の画面操作エージェントを新規開発すること、Computer Use の承認を回避することは対象外とする。最初の起動・撮影確認だけで GUI 検証全体を成功扱いにしたり、ただちにマージ条件へ接続したりもしない。

## 3. 公開側と非公開側をどう分けるか

### 公開の `hide212131/hane`

Hane 本体、通常のテスト、公開できる検証部品、シナリオの意図、この設計と ADR を置く。既存の CI、レビュー、修正ループ、GUI 検証の要否判定もここに残す。

検証対象は Pull Request の正確な head SHA とする。ブランチ名や `main` の最新状態を代用しない。Pull Request 用の仮のマージコミットを、head SHA の実アプリとして報告しない。

### 非公開の制御用リポジトリ

GitHub に新しく作る通常の private repository を使う。名前の候補は `hide212131/hane-gui-ci` であり、この設計の記録時点では作成を行わない。

Mac の runner をこのリポジトリにだけ登録する。実行依頼の受付、承認の確認、信頼する検証手順の選択、Mac のジョブ起動、証拠の回収を担当させる。[GitHub の説明](https://docs.github.com/en/actions/concepts/runners/self-hosted-runners)では、リポジトリ単位の runner はそのリポジトリ専用である。

将来作る構成の例は次のとおり。ファイル名は設計上の例であり、既存の実装ではない。

```text
hane-gui-ci/
  .github/workflows/validate.yml
  scripts/validate.sh
  README.md
```

`validate.yml` は許可した制御用ブランチの定義だけを使う。`validate.sh` は検証処理を呼ぶ制御用のスクリプトとする。Hane 本体をこのリポジトリへコピーして二重管理しない。

対象 Pull Request が変更した workflow、シナリオ、判定スクリプトを、同じ Pull Request の合格を決める信頼済みの設定として自動採用しない。制御側で承認した版の検証手順を使い、Hane の対象 SHA と検証手順の版を別々に記録する。公開側の検証部品を更新した場合は、制御側が使う版も別途確認して更新する。

これは「どの処理を Mac に実行させるか」の権限を分ける構成であり、実行するアプリを隔離する仕組みではない。

## 4. 信頼と権限の条件

### 実行してよい変更を限定する

初期運用では、GitHub API で再取得した情報を使い、対象が open・非 draft・same-repository の Pull Request であることを確認する。既存の controller が許可する投稿者・作成経路を満たしていることに加え、人がその exact head SHA の実行を承認していることを求める。GitHub の実行者の権限と、対象コードを信頼する判断は別に確認する。

fork、許可していない依頼者、未知のシナリオ、古い SHA、期限切れの承認は実行しない。CI や AI レビューが成功していても、ローカルで安全に実行できることを保証したものとは扱わない。修正 push 後は承認も新しい SHA に対して取り直す。

承認の保存方法は最初の制御用ワークフローで決める。初期の手動 dispatch 自体を承認として扱う場合も、権限を確認した実行者・対象 SHA・実行世代を記録する。GitHub のプランに依存する Environment の承認機能が使えることを前提にはしない。

### コードの実行と GitHub への書き込みを分ける

GitHub 側の依頼受付・結果報告ジョブと、Mac 側のビルド・実行ジョブを分ける。Pull Request へのコメントや status の書き込み権限、非公開側への dispatch 用認証情報、GitHub App の秘密鍵を Mac のビルド・実行環境に渡さない。checkout した作業コピーにも認証情報を残さない。

`GITHUB_TOKEN` の権限は、その workflow を実行するリポジトリに限定される。公開側から非公開側へ依頼する場合と、非公開側から公開側へ結果を報告する場合には、それぞれの目的に限定した認証が必要になる。[GitHub の認証説明](https://docs.github.com/en/actions/concepts/security/github_token)を参照する。GitHub App の短期トークンを第一候補とし、対象リポジトリと API 権限を後続実装で最小限に確定する。既存の Codex レビュー依頼用トークンを兼用しない。

ただし、self-hosted runner 自体の登録情報やジョブ用の認証情報まで消せるという意味ではない。同じ OS ユーザーで動く対象コードからそれらへ影響が及ぶ危険は残る。「別ジョブにした」「環境変数を消した」だけで、安全な隔離ができたとはしない。

### 非公開にしても残る危険

ビルドもコードの実行として扱う。Hane 本体だけでなく、ビルド用処理や依存関係の処理も対象になる。対象コードは同じユーザーのファイル、runner の作業領域、後続ジョブ、ネットワークへ影響し得る。[GitHub の安全上の注意](https://docs.github.com/en/actions/reference/security/secure-use#hardening-for-self-hosted-runners)は、private repository でもこの問題が残ると説明している。

初期の Mac は専用 OS ユーザーで動かし、個人文書、ブラウザーの個人セッション、SSH agent、不要なクラウド認証を持ち込まない。専用ユーザーと一時ディレクトリは事故や情報露出を減らすためであり、任意の悪意あるコードを封じ込める保証にはしない。より広い変更を無人実行する前に、専用 Mac または初期化できる検証環境とネットワークの制限を決め、この文書を更新する。

侵害や予期しない常駐プロセスが疑われた場合は runner を止め、認証情報の失効と環境の復旧を行う。作業ディレクトリの削除だけで安全に戻ったとは判断しない。

## 5. Mac の画面環境をどう扱うか

ユーザーがログインしている画面環境で動く常駐処理を使う。macOS では LaunchAgent と呼ばれる方式である。システム側の常駐処理と画面を扱う処理の違いは [Apple TN2083](https://developer.apple.com/library/archive/technotes/tn2083/_index.html)、runner のサービス設定は [GitHub の手順](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/configure-the-application)を参照する。

初めから常駐化せず、ログイン中の Terminal、同じユーザーで開始した runner、常駐起動した runner の順に、同じ検証を実行する。前の段階の成功を、次の段階の動作保証にしない。

実行前には、専用ユーザーの画面セッションを使えること、必要なウィンドウを取得できること、撮影と入力に必要な権限が実際の起動経路で有効なことを確認する。画面収録、アクセシビリティ、System Events を使う場合の Automation など、要求された権限を対象機で確認し、人が許可する。ChatGPT に付けた権限を借りたり、許可の保存先を直接書き換えたりしない。

初期ポリシーでは、ロック、ログアウト、別ユーザーへの切り替え、権限不足、画面の取得失敗を `blocked` とする。自動ログインや自動アンロックを実装の前提にしない。画面の状態を判定できない場合も成功にしない。

同じ Mac の画面を使う検証は一度に一つだけにする。GitHub のジョブ制御だけでなく、Mac 側でも排他と後片付けを確認する。普段の操作や他の画面操作ツールと競合した場合は、結果の信頼性を確認できるまで停止する。

## 6. 検証コマンドの責務

`gui-validate` は、これから用意する検証コマンドの仮称とする。最初から全操作を外部公開する大きな API は作らず、既存の起動・撮影・入力の部品を、シナリオと合否確認でまとめる。

### 実行の前後を管理する

テスト文書、`HANE_STATE_DIR`、ログ、画像の保存先を実行ごとに分ける。対象の checkout が要求された SHA と一致し、必要な変更が作業コピーに混入していないことを確認する。ビルド条件、機能フラグ、起動したバイナリの識別情報、検証手順の版を残す。

起動完了と対象ウィンドウを確認してから入力を送る。計測用機能によって内部状態を直接設定するシナリオは、その事実を記録し、通常の OS 入力を通した証拠と区別する。シナリオが途中で止まった場合にも、どこまで観測したかを残す。

終了時は、その検証で起動したプロセスだけを停止する。入力方式など、変更した設定を復元する。他の Hane、個人文書、無関係なプロセスをまとめて終了・削除しない。後片付けが失敗した場合は次の検証を開始しない。

### 操作ではなく、結果を確認する

| 確認する範囲 | 主に使う方法 | 合格の根拠 |
| --- | --- | --- |
| GPUI 内の入力処理やスクロール先 | 実画面部品へのイベントテスト | 関係する状態の変化や不変条件 |
| 実アプリの起動・描画 | 対象ウィンドウの取得と撮影 | 対象実行のウィンドウと、必要な表示を確認した記録 |
| OS を通した入力・保存 | 入力用補助プログラムと保存結果の読み取り | 期待した文書が実際に保存されたこと |
| 日本語入力や候補・未確定文字 | 実際の入力方式を使う操作と画面確認 | 入力経路、確定後の内容、必要な描画をそれぞれ確認した記録 |

たとえば日本語入力では、入力命令を送っただけで終えず、変換・確定を経た文書を保存して内容を比較する。候補表示や未確定文字の描画は別の観点として確認する。完成済みの日本語文字列を直接入れるだけでは、入力方式の検証を済ませたことにはしない。

シナリオの必須集合は、信頼する版の検証ポリシーから選ぶ。現在の GUI requirement classification は検証の要否を決めるものであり、それだけで必要な操作の一覧が完成したとは扱わない。変更に必要なシナリオが未実装・未実施なら `blocked` とし、起動・撮影だけの結果に縮めて `pass` にしない。

## 7. GitHub との受け渡し

### 検証依頼

初期は非公開側の手動 `workflow_dispatch` で始める。自動依頼を追加する段階でも、公開側が送るのは限定したデータだけにする。Issue 本文の任意コマンド、シェル断片、任意の取得先 URL を Mac へ実行指示として渡さない。

| 情報 | 契約 |
| --- | --- |
| 対象リポジトリ・PR 番号 | 許可リストと GitHub API の再取得結果で照合する |
| `target_sha` | 省略していない head SHA。要求時・実行直前・結果反映直前に照合する |
| 依頼 ID・実行世代 | 同じ依頼の再配送と、明示的な再実行を区別する |
| 検証ポリシー・シナリオ集合 | 制御側が承認した版と許可した識別子だけを受け付ける |
| 承認・有効期限 | 依頼者の権限、承認した SHA、失効・期限切れでないことを照合する |

入力値は型・範囲を検査し、シェルコードに文字列展開して実行しない。制御側の定義を対象コードの作業コピーから読み込まない。

自動運用では既存の順序を守る。同じ SHA の必須 CI が成功し、レビューが完了し、指摘がある場合は Copilot pre-GUI routing が `continue-validation` であることを確認する。`fix` / `blocked` や CI 失敗なら Mac を使わない。初期実証の手動実行は別の証拠として記録し、自動のマージ条件を満たした結果として流用しない。

### 結果と証拠

結果の形式は版を持たせる。少なくとも、依頼 ID、実行世代、PR 番号、要求 SHA と実際に検証した SHA、制御用手順の版、実行条件、全体結果、シナリオごとの結果・理由、ログと画像の参照先を含める。機械可読な結果ファイルと、人が読む短い概要を分ける。

| 全体結果 | 条件 |
| --- | --- |
| `pass` | 必須シナリオをすべて実施し、期待する結果と必要な証拠を確認できた |
| `fail` | 実行・観測できた検証で、製品が期待する挙動を満たさなかった |
| `blocked` | 権限・環境・未実装シナリオ・証拠不足などで、必要な確認を完了できなかった |

確定した製品の失敗と、環境の停止が混在した場合は、全体を `fail` として各理由を残す。製品の失敗を観測しておらず、必要な確認や後片付けが完了しなかった場合は `blocked` とする。クラッシュをすべて環境の問題にせず、起動した Hane の不具合として確認できた場合は `fail` にする。原因を特定できなければ、その不確かさを記録する。

GitHub 側は JSON に書かれた SHA や `pass` だけを信用しない。信頼する実行記録の run ID・試行・制御用 ref と照合し、受領した証拠の出所と現在の依頼世代を確認する。結果ファイルをコードとして実行せず、サイズや形式、参照先を検査する。検証対象が Mac 自体を侵害した場合の結果改ざんまで、この照合で防げるとは主張しない。

同じ SHA の `pass` / `fail` / `blocked` は、既存の設計どおり、いずれも final judge へ進む。GUI 検証が必須な場合、`pass` 以外で `ready` を許可しない。結果が別の SHA や古い実行世代に対応していたら履歴として残すだけで、現在の成功状態に反映しない。最終マージ条件でも再照合する。

### 待ち続ける状態と二重実行を防ぐ

ジョブの待機・実行中・取消し・期限切れは、製品の合否とは別の実行状態として管理する。同じ依頼の再配送では検証を重複実行しない。明示的な再実行には新しい世代を割り当て、遅れて返った以前の結果が上書きしないようにする。既存の全体設計にある期限付きの処理権と再試行の契約を使う。

Mac がオフラインでジョブを開始しない場合もあるため、GitHub 側で受付からの期限を持つ。ジョブ内のタイムアウトだけに依存しない。期限を過ぎたら、その世代を閉じて `blocked` として扱い、遅れて起動した Mac も実行直前に失効を確認して止まるようにする。世代を閉じた後の遅延結果から成功へ戻さない。

## 8. 画像を AI に渡す場合

最初は画像を保存し、人が確認できる経路を成立させる。AI による画像確認は別の段階で追加する。候補は Codex CLI に保存済み画像を渡す方法であり、Desktop やモバイルの Computer Use セッションの引き継ぎではない。

[公式 CLI リファレンス](https://developers.openai.com/codex/cli/reference)には画像入力 `--image` と、非対話実行の出力形式を指定する `--output-schema` がある。ただし、採用する固定版、認証方法、無人実行時の制約は実機で確認する。この設計では OpenAI API キーを必須にせず、既存契約の認証を使う経路を候補とする。Desktop の認証をコピーすれば動くという前提にはしない。

画像確認環境には、テスト用画像、期待する表示、必要な結果の説明だけを渡す。Pull Request のコードを実行する OS ユーザー・環境とは分け、そこから AI の認証情報を読めないことを確かめる。同じユーザーで別プロセスを起動しただけでは分離とみなさない。Computer Use、不要な外部接続や書き込みツールを使わせず、画像や文書内の命令はデータとして扱う。

画像はテスト用文書を開いた対象ウィンドウに限定する。全画面、個人文書、アプリ一覧、個人情報を含むファイルパスを、そのまま公開 PR へ出さない。非公開側のログ・画像は公開側の閲覧者に見えないため、公開してよい要約と、必要なら確認・除去処理をした証拠だけを公開側へ渡す。保存期間と公開先は実装時に設定する。

AI の画像判断で入力・保存の検査を代替しない。AI が利用上限や認証の問題で停止しても、操作テストの観測結果は保持する。画像確認を必須にしたシナリオでは、確認できなければ全体を `blocked` とする。参考情報として使う段階では、その判断をマージに必要な成功として数えない。

## 9. 段階的に実装する

| 段階 | 実施すること | 次へ進むための証拠 |
| --- | --- | --- |
| 0. 設計を記録する | この文書と ADR を追加し、全体設計から参照する | 役割、実行権限、合否、未実証の範囲をレビューできる。インフラは変更しない |
| 1. Terminal で検証する | 信頼する checkout で既存の起動・撮影処理を確認し、最小の入力・保存検査を加える | 対象 SHA、起動条件、テスト文書、画像、観測した保存内容、後片付けを記録できる |
| 2. runner の境界を確認する | 専用ユーザーと非公開リポジトリを用意し、手動承認した SHA を runner から検証する。その後に常駐起動を試す | Terminal、runner、常駐起動を区別した結果と、権限不足・ロック時の `blocked` を確認できる |
| 3. 依頼と報告を接続する | GitHub 側の受付・報告、SHA 照合、実行世代、排他、期限、認証の分離を実装する | 二重依頼、途中の push、古い結果、Mac 不在でも、誤った成功や無期限の待機を生じない |
| 4. 必須シナリオと進行判断を接続する | 必要な入力・日本語入力・スクロール・ファイル操作等を揃え、3結果から final judge へ接続する | 必要なシナリオと証拠が揃わなければ `ready` にならず、新しい SHA で検証をやり直す |

段階 1 と 2 の起動・撮影の成功は経路の実証であって、段階 4 の包括的な GUI 検証の成功ではない。画像の AI 確認は段階 3 以後に別途試せるが、段階 1 の着手条件にしない。初期の exact-SHA 手動承認を外す場合は、対象コード・端末・認証情報のリスクを再評価し、設計変更を先に行う。

### 最初の実装 PR

次は、既存 `scripts/capture.sh` を出発点に、テスト文書と設定を実行ごとに分け、起動・撮影・終了の証拠を残す最小の検証処理を実装する。続いて、既存の入力処理に保存内容の検査を組み合わせる。製品の期待不一致と環境不足を区別できるところまでを確認する。

この PR では、新しい非公開リポジトリ、クロスリポジトリ認証、自動 dispatch、最終マージ条件をまとめて導入しない。対象 Mac の実行確認をせずに、以降の段階を完了扱いにしない。

## 10. 実装前に確定する項目

非公開リポジトリの正式名と管理者、GitHub App の分離単位と最小権限、専用ユーザーと権限を与える実行ファイル、結果形式・状態の保存先、シナリオの選択規則、待ち時間・再試行・保存期間の値は、該当する段階の PR で確定する。

未決定の値に推測の初期値を入れて運用開始しない。決定した内容はこの文書またはリンクした運用手順へ追記し、Issue にはそのリンクと実証結果だけを残す。
