# Rust + GPUI 超高速 WYSIWYG Markdown Editor 開発 RFP

## 1. 本RFPの目的

本案件では、TyporaのようにMarkdownの記法を意識せず、その場で文章を読みながら編集できるデスクトップエディタを開発する。

ただし、既存のWeb技術を利用したMarkdownエディタとは異なり、Electron、Chromium、WebView、DOM、HTML/CSSによる本文描画は使用しない。

RustとGPUIを使い、本文・カーソル・選択範囲・画像・コードブロックなどをネイティブに描画する。

本製品が最も重視する価値は機能数ではない。

**アプリを起動した瞬間に編集でき、巨大なMarkdownファイルでも入力が引っ掛からないことを最優先する。**

---

# 2. 製品コンセプト

製品の方向性を一文で表すと、以下とする。

> **「起動した瞬間に書ける、GPU描画の超高速・軽量Typora」**

対象はMarkdownを日常的に文章として書く利用者であり、高機能な統合開発環境を目指さない。

画面も極力単純にする。

```text
┌──────────────────────────────────────────┐
│ document.md                              │
├──────────────────────────────────────────┤
│                                          │
│  高速な Markdown Editor                  │
│                                          │
│  これは普通の文章です。                  │
│                                          │
│  これは 太字 です。                      │
│                                          │
│  • 項目1                                 │
│  • 項目2                                 │
│                                          │
│                                          │
└──────────────────────────────────────────┘
```

ファイルツリー、プラグイン、AI、ターミナル、Gitなどは初期版には搭載しない。

本文を書くことだけに集中する。

# 3. 必須技術

実装言語はRustとする。

画面描画にはZed IndustriesのGPUIを直接使用する。React、Node.js、gpuixなどの中間層は使用しない。

GPUIは現在、GPUを利用するUIフレームワークとして公開されており、文字入力、文字レイアウト、選択、クリップボード、キーボード入力などのサンプルも提供されている。 citeturn710457search0turn710457search1turn710457search7

初期構成は以下を基本とする。

```text
Rust application
      │
      ├── Document Core
      │
      ├── Markdown Parser
      │
      ├── Visual Model
      │
      ├── Editor
      │
      └── GPUI
              │
              ▼
             GPU
```

以下の技術は禁止する。

- Electron
- Chromium / WebView
- HTML DOMを本文編集の基盤として利用すること
- JavaScriptまたはTypeScriptを本文編集処理の必須経路に入れること
- Monaco Editor、CodeMirror、ProseMirror等を本文エディタとして組み込むこと

HTMLを書き出す機能を将来追加することは禁止しない。禁止対象は、**エディタ自身の描画・編集基盤としてWebブラウザを使うこと**である。

# 5. WYSIWYG編集の定義

本製品では、Markdownソースとプレビュー画面を分離しない。

以下のMarkdownが存在するとする。

```markdown
# Hello

This is **important** text.
```

通常時には次のように表示する。

```text
Hello

This is important text.
```

見出しは見出しとして表示し、`#` は表示しない。

太字は太字として表示し、`**` は表示しない。

ただし、「important」を編集するときには必要に応じてMarkdown記号を表示できるようにする。

```text
This is **impor|tant** text.
```

カーソルが外れれば再び、

```text
This is important text.
```

へ戻る。

この動作を本RFPでは**Markdown記号の段階表示**と呼ぶ。

エディタ内部の正式なデータは、常にMarkdownソースそのものとする。

画面上の装飾された文章を正式データとして持ち、保存時にMarkdownへ逆変換する設計は禁止する。

---

# 6. 最重要設計原則

## 6.1 Markdownソースを唯一の正とする

文書は常に次のようなMarkdownとして保持する。

```markdown
# Title

Hello **world**.
```

解析結果は、

```text
Heading
source: 0..7

Strong
source: 15..24
```

のように、必ず元Markdown上の位置と結び付ける。

画面上の位置からMarkdown上の位置へ、またMarkdown上の位置から画面上の位置へ変換できなければならない。

この対応関係は、カーソル、選択、IME、Undo/Redoのすべてで共通して利用する。

---

## 6.2 入力処理では解析完了を待たない

キー入力は次の順序で処理する。

```text
Keyboard / IME
      │
      ▼
Documentを即時変更
      │
      ├─────────────► Parser
      │                 非同期処理
      │
      ▼
現在の表示を即時更新
      │
      ▼
GPUI
      │
      ▼
GPU
```

Markdown解析が終わるまでキー入力を待たせてはならない。

画像読み込み、Markdown全体解析、シンタックスハイライト、ファイル保存なども、入力処理を待たせてはならない。

バックグラウンド処理には文書の世代番号を付与する。

例えば、

```text
revision 100 → parse開始
revision 101 → ユーザー入力
revision 102 → ユーザー入力

revision 100 → parse終了
```

となった場合、古いrevision 100の結果によってrevision 102の表示を上書きしてはならない。

# 7. Markdown解析方式

Markdownの意味を正しく解釈する処理には、原則として `pulldown-cmark` を使用する。

`pulldown-cmark` はMarkdownの解析結果と、元Markdown上のバイト範囲を組にして取得できる `into_offset_iter()` を提供しているため、本製品で重要となる「表示位置とソース位置の対応」に利用できる。 citeturn208652search0turn208652search2

ただし、巨大ファイルで毎回文書全体を解析してはならない。

そこで解析を二段階に分ける。

```text
                 Document
                     │
          ┌──────────┴──────────┐
          │                     │
          ▼                     ▼
   即時表示用の局所解析      正式な全体解析
   active block周辺          background
          │                     │
          └──────────┬──────────┘
                     ▼
                 Visual Model
```

入力直後には、現在編集中の段落または周辺ブロックを解析する。

文書全体の正式な解析はバックグラウンドで行い、終了後に表示モデルと整合させる。

Tree-sitterをMarkdown文書の唯一の解析器として利用することは、初期版では要求しない。

Tree-sitter自体は差分解析を目的とした仕組みだが、現在公開されているMarkdown文法側には、正確さが重要な用途には推奨しないという注意があるためである。 citeturn208652search7turn208652search9

# 8. 文書データ構造

巨大な文書に対する途中挿入・削除で文書全体をコピーしてはならない。

そのため、単一の巨大なRust `String` を編集用の主要データ構造として使用することは禁止する。

以下のいずれか、または同等の計算量を持つ構造を採用する。

```text
Rope
Piece Tree
Piece Table
B-tree based text buffer
```

採用する方式は、性能試験を行った上で決定してよい。

必要条件は、文書サイズに比例した文字列コピーを通常の1文字入力ごとに発生させないことである。

Zed自身もテキスト処理にRopeやB-tree系構造を利用しており、テキスト位置や編集範囲を木構造で管理している。 citeturn998777search1turn998777search4

ただし、Zed内部の `text`、`editor`、`language` 等のcrateをそのまま利用することは本RFPの必須条件としない。

GPUI以外は、製品に必要な最小構成として独立して実装することを優先する。

# 9. 表示単位

文書全体を一つの巨大なGPUI要素として描画してはならない。

Markdownを表示用のブロックへ分割する。

例えば、

```text
Document
 │
 ├── HeadingBlock
 ├── ParagraphBlock
 ├── ListBlock
 ├── QuoteBlock
 ├── CodeBlock
 ├── ImageBlock
 └── ParagraphBlock
```

とする。

各ブロックは最低限、以下を保持する。

```text
source_range
visual_height
layout_cache
style_runs
revision
```

変更されたブロックだけレイアウトを破棄する。

変更されていないブロックの文字レイアウト結果は再利用する。

---

# 10. 画面外を描画しない

巨大Markdownへの対応では、GPUの速度だけに依存してはならない。

10万段落存在していても、画面に20段落しか見えていなければ、原則としてその周辺だけをGPUIへ渡す。

```text
Block 00001
Block 00002
...
Block 48190

-----------------------
Block 48191  ← 描画
Block 48192  ← 描画
Block 48193  ← 描画
Block 48194  ← 描画
-----------------------

Block 48195
...
Block 99999
```

画面外のブロックについては高さと位置を計算するための情報だけ保持し、GPU描画用要素を毎フレーム構築しない。

GPUIには仮想化したリストを描画する `uniform_list` のサンプルがあるため、実装時にはその設計も参考にする。 citeturn710457search0

ただしMarkdownは各ブロックの高さが異なるため、固定高さのリストをそのまま適用するのではなく、可変高さに対応した文書用の仕組みを設計する。

# 11. 初期版で対応するMarkdown

初期版では、日常的な文章作成に必要なMarkdownに絞る。

必須とするのは以下である。

- 見出し、段落、改行
- 太字、斜体、取り消し線、インラインコード
- 箇条書き、番号付きリスト、チェックボックス
- 引用、コードブロック
- リンク、画像、水平線

表については第1版後半で実装する。

数式、Mermaid、埋め込みHTML、動画、プラグイン独自記法は初期版の対象外とする。

これらを追加するためにWebViewを導入してはならない。

# 12. 日本語入力

日本語入力は初期版の必須条件とする。

IMEによる未確定文字列について、

```text
今日は
    ↓
きょ
    ↓
きょう
    ↓
今日
```

という変換途中の状態も正しく表示する。

変換中の文字列について、選択範囲、下線、確定、キャンセル、カーソル移動を扱えること。

GPUIの現在の入力APIおよびサンプルには、選択範囲に加えてIMEの変換途中を表す `marked_range` やUTF-16位置との変換処理が存在するため、それを基本に実装する。 citeturn710457search1turn710457search8

日本語入力中にMarkdown解析結果が変わっても、IMEセッションを破壊してはならない。

# 13. カーソルと選択

WYSIWYGエディタで最も重要な内部機能の一つとして、表示位置とMarkdown位置の対応を実装する。

例えば、

```markdown
これは **重要です**。
```

を、

```text
これは 重要です。
```

と表示している場合、

```text
これは 重|要です。
```

という画面上の位置を、

```markdown
これは **重|要です**。
```

というMarkdown上の位置へ正しく変換する。

以下の操作すべてで対応関係が壊れないこと。

- マウスクリックによるカーソル移動
- 左右上下キーによる移動
- Shiftを利用した選択
- 複数のMarkdown装飾をまたぐ選択
- 日本語IMEによる入力

この機構には単体テストを重点的に作成する。

---

# 14. Undo / Redo

Undo / RedoはMarkdownソースに対して行う。

一文字ごとではなく、通常の文章入力として自然な単位にまとめる。

例えば、

```text
hello
```

と連続入力した場合、Undoを5回要求するのではなく、一定時間内の連続入力を一つの操作として戻せるようにする。

Markdownの表示状態はUndo履歴へ保存せず、ソースから再生成する。

---

# 15. ファイル操作

初期版では以下だけを実装する。

```text
New

Save
```

自動保存を実装する。

自動保存処理によって入力が止まってはならない。

保存中に次の編集が行われた場合も、保存対象のrevisionを明確に管理する。

# 16. 性能要求

ここで示す値は既存GPUIが保証している性能ではない。

**本製品で達成を目指す受入基準**として設定する。

基準機はApple Silicon、16 GB以上のメモリを搭載したmacOS機とする。

### 起動

プロセス開始から入力可能になるまでを測定する。

| 状態 | 要求 |
|---|---:|
| Warm start 中央値 | 150 ms以下 |
| Cold start 中央値 | 400 ms以下 |
| 起動直後の待機画面 | 不可 |
| 起動後のバックグラウンド初期化 | 許可 |

「全機能の準備が完了してから画面を出す」のではなく、編集画面を最優先して表示する。

### 入力遅延

キーイベントを受け取ってから新しい文字がGPU描画対象になるまでを測定する。

| 条件 | 要求 |
|---|---:|
| 通常文書 p95 | 8 ms以下 |
| 通常文書 p99 | 16 ms以下 |
| 100 MB文書 p95 | 16 ms以下 |
| 100 MB文書 p99 | 33 ms以下 |

Markdown解析、画像処理、保存などを理由として入力処理が50 ms以上停止する状態を通常動作として許容しない。

### 巨大ファイル

最低限、以下を自動性能試験へ含める。

```text
1 MB Markdown
10 MB Markdown
100 MB Markdown
100,000 paragraph Markdown
```

100 MBの文書を開いた状態でも、編集位置付近での通常入力が文書サイズに比例して遅くならないこと。

### スクロール

120 Hz環境では120 frames per secondを目標とする。

巨大文書でも最低60 frames per secondを安定目標とし、画面外の文章数によって描画負荷が大きく増えないこと。

GPUIはZedで高いフレームレートを目標として設計されているが、本製品でも独自にフレーム時間を計測し、GPUIを採用しただけで高速と判断してはならない。 citeturn710457search6

# 17. メモリ要求

Electronとの比較を目的にするのではなく、絶対値として軽量であることを確認する。

初期目標値を以下とする。

| 状態 | 目標 |
|---|---:|
| 空文書・起動直後 | 60 MB以下 |
| 10 MB Markdown | 120 MB以下 |
| 100 MB Markdown | 350 MB以下 |

ただしGPUドライバ等によるOS側メモリ計上差があるため、測定方法を固定して継続測定する。

同一文字列をMarkdownソース、AST、表示用文字列の3か所へ完全複製するような設計は避ける。

# 18. Performance Harness

性能は手作業で確認するだけではなく、自動測定できるようにする。

最低限、以下を計測する。

```text
startup_time
file_open_time
keystroke_to_paint
frame_time
parse_time
layout_time
memory_usage
```

開発中は性能の中央値だけでなく、95パーセンタイルおよび99パーセンタイルを見る。

平均値が高速でも、ときどき100 ms停止するエディタは本案件では不合格とする。

特に `keystroke_to_paint` を最重要指標とする。

# 20. GPUIの利用方針

GPUIを単なるウィジェット集として利用するのではなく、エディタ本文では必要に応じて専用のGPUI Elementを実装する。

本文については、

```text
layout
prepaint
paint
```

の各段階を意識し、文字レイアウト結果を可能な限り再利用する。

同じ段落が変更されていないのに、入力のたびに再度文字整形を行ってはならない。

変更の影響範囲を、

```text
Document
 ↓
Block
 ↓
Line
 ↓
Text Run
```

の順で狭める。

# 23. 開発段階

## Phase 0 — 技術検証

最初に完成品を作り始めない。

以下だけを持つ小さな実験アプリを作る。

```text
GPUI Window
+
1つの巨大Text Buffer
+
カーソル
+
日本語入力
+
太字表示
+
スクロール
```

この段階で10 MBおよび100 MB文書の入力遅延を測る。

性能上の重大な問題が見つかった場合は、製品実装へ進む前に構造を変更する。

## Phase 1 — Plain Text Editor

Markdown描画を行わない、高速なテキストエディタを完成させる。

カーソル、選択、IME、Undo/Redo、スクロール、巨大ファイルをここで完成させる。

## Phase 2 — Markdown Presentation

見出し、太字、斜体、コード等を画面上で装飾する。

この段階ではまだMarkdown記号を完全には隠さなくてもよい。

## Phase 3 — Typora-style Editing

Markdown記号の段階表示と、Source ↔ Visual位置変換を完成させる。

ここで初めて本製品の主要価値が成立したと判断する。

## Phase 4 — Polish

画像、表、自動保存、Recent Files、設定、テーマ等を追加する。

# 25. 成功判定

このプロジェクトでは、機能の数ではなく次の順序で成功を判断する。

**第一に、入力が速いこと。**

巨大ファイルでもキー入力が文書全体の解析やレイアウトを待たないこと。

**第二に、WYSIWYGとMarkdownソースが完全に対応すること。**

見た目を編集しても、保存されたMarkdownが壊れないこと。

**第三に、軽いこと。**

ElectronやWebViewを導入せず、起動時間とメモリ使用量を継続して測定すること。

**第四に、単純であること。**

機能を増やすことで上記三点を悪化させないこと。

# 26. 提案者に求める回答

実装提案時には、単に「実現可能」と回答するのではなく、次の内容を提示すること。

1. Text Bufferとして採用するデータ構造と、その理由。

# 28. 最終的に目指す状態

目標は「高機能なMarkdownアプリ」ではない。

次の操作感を実現することである。

> アイコンをクリックする。  
> すぐ文章が見える。  
> そのまま打つ。  
> ファイルが巨大でも挙動が変わらない。  
> Markdownを書いていることを普段は意識しない。

そのため、開発中に機能追加と性能のどちらを優先するか判断が必要になった場合は、原則として性能を優先する。

**本製品の差別化要因は、RustやGPUを使っていること自体ではない。  
利用者が処理待ちを意識しないMarkdown編集を実現することである。**
