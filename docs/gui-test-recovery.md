# GUIテストの診断・復旧と継続

画面取得や入力の失敗は、テストを終了する結論ではなく、復旧対象を特定するための観測である。必要なGUI evidenceが揃うまで受入・mergeを保留しつつ、診断・復旧と実行可能な作業を続ける。意味判断・受入判断の正本は[Commander Policy](aadw-command-policy.md)、既存の実行経路は[ローカルGUI検証](local-gui-validation.md)と[CLI操作説明](local-gui-validate-cli.md)とする。

## 1. 実行経路と開始前確認

- macOSのGUIはMac上で操作する。
- **WindowsのGUIは、ChatGPTアプリ（旧Codexアプリ）の「接続」でリモート設定したWindows環境上のChatGPTアプリから直接操作する（以下「接続先のWindows版ChatGPTアプリ」）。Mac経由でVMを操作する経路はNG。** Mac上のVMwareウインドウへのクリック・キー送信・ドラッグを通常経路にも復旧候補にも使わない。MacからWindowsの調整をする場合は、利用者に送信を許可された既存Windowsチャットへ依頼し、その結果を読む。適切なチャットへの送信許可がない場合だけ、依頼内容を具体化して許可を求める。
- PRのcurrent head、必要なbase context、ビルド元SHA、実行ファイルの絶対パス、ホスト・OS・ログインセッションを記録する。既存のバイナリを名前だけで採用しない。
- 専用の`HANE_STATE_DIR`と一時workspaceを用意し、通常のHaneや利用者の文書から隔離する。未保存編集を含むケースはテストfixtureで再現する。
- 同じデスクトップで別テストが動いていないか確認する。GUI占有中は既存の排他に従い、待つ間にログ調査・証拠整理・ビルドなど画面に触れない作業を進める。
- 画面取得だけで操作可能としない。対象ウインドウの取得、画像、無害なクリック、テスト欄へのキー入力と結果の再取得を個別に確認する。IMEシナリオには実際の未確定文字・変換候補の観測も必要。

## 2. 失敗したら同じセッションで行うこと

1. **最初の失敗を保存する。** 例外全文、時刻、操作、PID・実行パス、画像/AX情報の有無、直前に成功した操作を残す。画面が取得不能ならその事実とログを残す。
2. **失敗範囲を比較する。** 起動、ウインドウ列挙、画像取得、座標入力、AX要素操作、キーボード、IME、判定のどこが成立していないか分ける。同一ホストのFinder/Explorer等でも軽量な状態取得と無害な操作を試し、アプリ固有か操作基盤共通かを切り分ける。
3. **一つだけ対処して再観測する。** 古いapp/window参照の取得し直し、対象の前面化・通常表示への復帰、専用テストアプリの再起動、操作接続の再初期化、所有を確認できる専用helperの再起動を、症状と利用中のツール仕様に応じて選ぶ。各段階で軽量確認を実施し、何が戻って何が残ったかを記録する。
4. **同じ条件の再送から診断へ切り替える。** 再起動後もFinder/Explorer等で同じエラーなら、Haneの再起動を繰り返さず操作基盤を調べる。JSセッションresetはOS側helperの再起動と同義ではない。helperの所有関係や再接続方法が不明なら、ログ・プロセス親子関係・現行ツール仕様を調べる。
5. **復旧を確認して元のテストへ戻る。** 画像取得と必要な入力経路を小さく確認してから、失敗した受入シナリオを最初から実行する。途中でfixtureを変更・復元した場合はその前提も作り直す。PR head/baseの鮮度を再確認し、復旧の確認だけを受入passにしない。

macOSのCUAが復旧しない場合も、既存のHosted GUI ValidationやローカルCLIで同じ受入条件のどこまで観測できるか確認する。起動・ウインドウ・画像の確認だけを行うCLIでは、Finder dropやIMEなど対象外の条件を合格にできない。選択した経路が必要な入力・表示・判定を実際に観測できる場合に限って再実行し、観測できない条件は残す。Windowsの必須GUIをMacのHosted/CLIで代用しない。

### 再起動の対象を取り違えない

- 停止前に実行ファイルの絶対パス、PID・親PID、起動引数、所有チャット/テストを照合する。自分の隔離テストプロセスだけを通常終了し、終了を確認してから同じ候補を再起動する。通常終了が効かず強制終了が必要な場合も、PIDを再確認しテストデータの範囲に限定する。
- macOSでは`ps -axo pid,ppid,stat,command`など、Windowsでは`Get-CimInstance Win32_Process`の`ProcessId` / `ParentProcessId` / `ExecutablePath` / `CommandLine`などで識別できる。取得できない値は推測で埋めない。
- `pkill Hane`や`taskkill /IM hane.exe /F`など名前による一括停止をしない。共有GUIロックはファイルを消して奪わず、所有プロセスの終了・OSロック解放を確認する。詳細は[CLIの排他と後片付け](local-gui-validate-cli.md)を参照。
- 他チャットのhelper、Codex本体、WindowServer、Explorer全体、OS/VMの再起動やログアウトを、専用helperの再起動と同列に実施しない。共有の作業を止める操作や手動解除が必要な認証・画面ロックは、必要な対応を特定して利用者へ依頼する。その間も独立した作業を進める。
- 現在のツールで許可される操作経路を使う。取得したエラーを理由に、別のAPIや非公開のUI操作経路で制約を回避しない。

## 3. macOSで確認されたこと

### PR #507: 表示の復旧と座標入力の障害を分ける

2026-10-18のチャット`01a14920-9e75-72b0-b678-a816d5630d72`では、検証用Haneを実行パスとPIDで識別して通常終了・再起動し、画面表示とAX情報が戻った。しかし座標クリックは`noWindowsAvailable`のままで、Finderでも再現した。CUAのJS接続resetと専用操作プロセスの再起動でも入力は復旧しなかった。

当初の「フルスクリーンが原因」という説明は、同チャットの最終調査で**通常ウインドウだった**と訂正されている。フルスクリーンは確定原因として採用しない。ウインドウ列挙失敗がMac側の座標操作経路に共通することまでは観測できたが、その内部原因と解決策は未確定である。

再発時はHaneの再起動だけを重ねず、AX/画像と座標入力を比較し、同じホストのFinderで再現するかを先に確認する。AX要素やキーボードが使えても、実ポインタードラッグが必要な受入条件をショートカットで代用しない。Windowsで成功したdrop確認もmacOSのFinder確認の代替にはしない。

### PR #497: 貼り付け成功はIME変換の証拠にならない

チャット`01a1481a-7baa-7de3-9bce-2041933a5f0d`では、Macの入力sourceを切り替えてもCUAの文字送信は確定済み英字として届き、IME変換は発生しなかった。rename欄への入力が本文へ入った試行もあり、fixtureを復元してその結果を無効にした。

入力前にフォーカスを確認し、未確定文字・候補・確定/取消を別々に観測する。入力source変更やアプリ再起動だけでIMEを合格にしない。このMacのIME入力経路は当時未解決。一方、Windows実機環境からの直接操作では日本語IMEの未確定文字・候補と取消を観測でき、Windowsの検証を続行できた。両OSの結果は分けて残す。

## 4. Windowsの直接操作

Windows実機環境での実績と、2026-10-18に既存Windowsチャットへ照会して得た手順をここに集約する。Mac経由VM操作は選択しない。

### JSカーネル用の一時ディレクトリ欠落を復元して復旧

同日のチャット`01a14803-a6bf-7d92-9102-bb5007ace138`では、CUAと通常のJS実行が次の例外で失敗していた。

```text
failed to write kernel assets:
指定されたパスが見つかりません。 (os error 3)
```

画面取得以前のJSカーネル準備段階の障害であり、`js_reset`だけでは直らなかった。実行ファイル・モジュール・プロセス・Tempを調査し、対象の`node_repl`が保持する一時ディレクトリ2個が存在しないことを`Test-Path`で確認した。別の正常プロセスでは対応するディレクトリが存在した。

**特定した欠落ディレクトリだけを空ディレクトリとして復元し、各JSカーネルをreset・再初期化すると復旧した。** Codex本体・`node_repl`プロセス・Windowsの再起動は不要だった。続けてCUAの`cua.getState()`、単純なJS実行、Windowsアプリ列挙、Haneの画面取得・入力・Explorerからの実dropが成功した。

再発時は、現在のログと対象プロセスの診断情報から、**今回失われた正確なパス**と所有関係を特定して存在を確認する。ディレクトリ名は実行ごとに変わるため、過去の`.tmp...`名をコピーしない。カーネル資産生成先として使っている通常のディレクトリであることを確認できた場合に限り、例えば次の操作でそのディレクトリだけを復元する。

```powershell
# $kernelTempPathには今回の診断で確認した絶対パスを設定する。
Test-Path -LiteralPath $kernelTempPath
New-Item -ItemType Directory -Path $kernelTempPath
```

その後、利用中のCUA/JSツールのresetと初期化仕様に従い、軽量確認から元シナリオへ戻る。一時領域全体の削除、権限の一括緩和、ランダムなディレクトリ作成は行わない。診断でプロセス内部の情報を調べる場合も対象パスに限定し、メモリ全体や認証情報をログへ出さない。

**欠落した理由は未確定。** Temp清掃・画面ロック・RDPを原因と断定しない。再発防止として、このテストと操作ランタイムが使用中の一時ディレクトリを清掃対象から外し、古い不要物と稼働中の領域を区別する。ただし、これを実際の削除原因の確定とは扱わない。

証拠はWindows側の`%USERPROFILE%\.codex\sessions\2026\10\17\rollout-2026-10-17T12-59-21-01a14803-a6bf-7d92-9102-bb5007ace138.jsonl`にある。当時の行4128に欠落パス検出、4141に復元、4162・4173にJS/アプリ列挙の再試験が記録されている。照会先の回答も同チャットの2026-10-18の履歴に残る。

### 入力・ダイアログ・証拠保存の失敗を分ける

| 症状 | 成功した対応と再観測 |
| --- | --- |
| Explorerの要素クリックが`point ... is outside window bounds` | 新しい画面を取得し、表示範囲内のファイル名座標を選んでクリックすると選択成功。長い一覧項目の要素中心が表示外だった例であり、座標を推測で再送しない。 |
| Ctrl+O後に独立ウインドウ一覧へOpenダイアログが出ない | 所有元Haneの画面と関連ダイアログを取得し、`Alt+n`でファイル名欄へ移動、パス入力→Enterで開けた。一覧にないことをダイアログ不在と決めない。 |
| 画像は表示されたが保存用JS変数が`undefined` | 画面表示とAPI戻り値を分け、現在の戻り値構造を確認して状態を`globalThis`に保持・再取得すると保存成功。描画障害と断定しない。戻り値欠落の内部原因は未確定。 |
| Keyhacによって入力の解釈を誤る可能性 | 開始状態を読んで試験中だけOFF、試験後に元の状態へ戻す。トレイの「フックをOFF」は現在ON、「フックをON」は現在OFFを表す。切替後はメニューを再取得して確認。既存の許可された補助スクリプトを使う場合も、実行完了と終了コードを確認する。 |

Openダイアログの障害が「5秒の入力遅延」で直ると確定した記録はない。固定秒数待ったことではなく、フォーカス・入力内容・開いた文書を順に確認する。Keyhacがカーネル資産生成エラーを起こした証拠もないため、二つの原因を混同しない。

Windowsのファイルopen転送先は、確認したPR #507の実装では`LOCALAPPDATA`と実行ファイルパスに依存する。専用テストの`HANE_STATE_DIR`だけで別プロセスへの転送まで隔離できたと仮定せず、current headの`crates/app/src/open_request.rs`を確認し、必要なアプリ用プロファイル領域も分離する。操作ランタイム自身が使うTempと、子のHaneへ渡すテスト用Tempを混同しない。

### ロック・RDP・セッション切替は成功実績と混ぜない

照会先がこのチャットとPR #485確認チャットを調べた範囲では、ロック解除、RDP再接続、`tscon`、セッション0/別ログオンセッションの変更で復旧した証拠はなかった。これらを確認済みの復旧コマンドとして載せない。実際にロック画面や別セッションが観測された場合は状態を記録し、利用者に必要な解除を依頼する。共有セッションを切断・ログアウトさせない。

### 既に照合できた実績

- PR #507のチャット`01a14803-a6bf-7d92-9102-bb5007ace138`では、開始時のKeyhacフック状態を記録し、試験中だけOFFにし、終了時に元のONへ戻してメニュー表示まで確認した。開始状態を記録せず一律ONへ戻さない。
- 同チャットでExplorer上の実ファイルを`pointer down → 押したまま移動 → release`してHaneの本文マーカーを確認した。ドラッグ後の画面だけでなく、押下・移動・解放のログを残す。OpenダイアログやCLIの成功だけをdropの証拠にしない。
- 未保存保護の確認では、専用テストstateの自動保存をOFFにして未保存マーカーを作り、別ファイルdrop後に本文・dirty表示・選択範囲とファイル内容が保持されたことを確認した。
- 既存の[Issue #414再試行記録](issue-414-windows-validation-retry-20261002.md)では、JS resetだけではhelperのウインドウ列挙timeoutが直らなかった。これは復旧成功例ではない。build/test成功をGUI成功とせず、OS側helper・セッションの診断へ進めるための失敗記録として読む。

## 5. 復旧できないときにも作業を引き継げる形にする

同じ条件で失敗した操作を無限に再送しない。比較観測・専用アプリ/接続/helperの復旧・正規経路の確認を進めても、利用者操作や共有基盤の修復が必要だと確認された場合は、その依存項目だけを保留する。利用者に依頼する前に、実行可能な診断・証拠保存・独立した検証を済ませる。

「画面が取れないのでできませんでした」だけで終了せず、次の引継ぎを保存する。

```text
対象: PR / head / 必要なbase / OS / host / build元・実行パス
未完了: シナリオIDと失敗した具体的操作
観測: 例外・時刻・ログ/画像・対象アプリと比較アプリの違い
実行済み対処: 変更した一項目 → 再観測結果（表示/座標/キー/IME）
結論: 確認済み原因 / 仮説 / 未確定を区別
継続済み: 独立して完了した検証・調査
必要な対応: 誰が何をすれば再開できるか（利用者操作は必要最小限）
再開手順: 軽量確認 → fixture準備 → 元シナリオ再実行 → SHA/証拠照合
後片付け: 専用PID・一時設定・Keyhac等の開始状態への復元
```

自動的な再開や未来の監視は設定していなければ約束しない。チャット再開時にはこの記録を読み、過去のblockedを現在の実行不能と決めつけず、復旧した層の軽量確認から再開する。

## 6. 更新のしかた

新しい復旧が成功したら、症状・切り分け・実際の操作・復旧後の元シナリオの結果・証拠の場所を追記する。試しただけの再起動を成功手順として追加しない。後から否定された原因説明は訂正する。これは追加のworkflow/state machineや必須のfull regressionを導入するものではない。
