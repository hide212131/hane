上下移動以外のコマンドや `set_selection` は目標Xをリセットする。短い行で到着位置がクランプされても、上下移動中の目標X自体は保持される。根拠：`crates/editor/src/lib.rs:218`、`:241`、`:268`。

### レイアウトを使えない場合

`move_vertical_by_layout` が失敗した場合は、`EditorCommand::MoveUp / MoveDown` にフォールバックする。

エディタコアは現在の物理行内の書記素数を目標カラムとして保持し、前後の物理行の対応位置へ移る。短い行では行末にクランプする。Markdownやフェンスの知識は持たない。

根拠：`crates/ui/src/view.rs:4076`、`crates/editor/src/movement.rs:86`。

### コードフェンスの表示行

| 行の種類 | 非開示時 | キャレット・選択・IMEによる開示時 |
|---|---|---|
| 開きフェンス | フェンス記号、言語指定、末尾空白を隠す。通常は空文字列・高さ0 | 物理行全体を表示し、通常のコード行の高さになる |
| コード本文 | リテラルなコードとして表示。空のコード行も高さを持つ | 同じくコード本文として表示 |
| 閉じフェンス | 改行を含む行全体を、表示幅0の隠し区間へ写像する。高さ0 | 生のフェンス行を表示し、通常のコード行の高さになる |
| 閉じフェンス後の空行 | 通常行として表示 | 通常行として表示 |

根拠：

- フェンスの識別：`crates/presentation/src/projection/mod.rs:2315`
- 開きフェンスの表示：`crates/presentation/src/projection/mod.rs:2474`
- 閉じフェンスの表示：`crates/presentation/src/projection/mod.rs:2565`
- 非開示時の高さ0：`crates/presentation/src/projection/mod.rs:229`
- コードブロック後の空行を通常行として扱う処理：`crates/presentation/src/projection/block.rs:296`

ブロックは次のブロックまで文書を隙間なく覆うため、後続の空行がコードブロックの所有範囲に含まれる場合がある。ただし、その空行までコード本文になるわけではない。根拠：`crates/markdown/src/block_index.rs:12`、`crates/presentation/src/projection/block.rs:17`。

**高さ0でも、フェンス行はレイアウト配列に残る。** 通常の `layout_block` は高さによる除外を行わず、空文字列の行も `LayoutLine` として追加する。対して表の非表示区切り行は、表用レイアウトで明示的に除外される。

根拠：`crates/presentation/src/layout.rs:982`、`:1004`、`:1095`。

コード行は等幅フォントで、表示される行の高さは通常の行高と同じ。コード専用の折り返し禁止分岐はなく、通常の幅・shaperに基づく折り返し経路を通る。開示されたフェンス行も長ければ折り返し対象になる。

根拠：`crates/presentation/src/display.rs:419`、`:880`、`crates/presentation/src/layout.rs:984`、`:1845`。

## (a) ↑で移動できない原因

### 候補の切り分け

| 候補 | コード上の判断 |
|---|---|
| ↑のキー割り当て漏れ | 本文向けの処理が存在する。フェンス直後だけ停止する説明にはならない |
| エディタコアが閉じフェンスを拒否する | コアの上下移動は物理行と書記素だけを扱い、フェンスを拒否しない |
| 閉じフェンスが表示行として存在しない | 高さ0でも `LayoutLine` として残るため、該当しない |
| 閉じフェンスへの移動結果が元の位置になる | 行選択、隠し区間の逆変換、成功判定をつなげると報告を説明できる |

### 原因となる具体的な経路

最小例を、改行を含む次の文字列とする。

````text
```
abc
```
|
````

実際の文字列は `"```\nabc\n```\n"`。`|` は末尾の空行先頭、バイトオフセット `12` を示す。

| 行 | 文書範囲 | 表示内容 |
|---|---|---|
| 開きフェンス | `[0, 4)` | 空文字列、高さ0 |
| コード本文 | `[4, 8)` | `abc` |
| 閉じフェンス | `[8, 12)` | 空文字列、高さ0 |
| 末尾空行 | `[12, 12]` | 空行、通常の高さ |

この状態で ↑ を押すと、以下になる。

1. `vertical_target` は直前の配列要素、すなわち閉じフェンス行を選ぶ。高さ0かどうかは確認しない。  
   根拠：`crates/presentation/src/layout.rs:816`
2. 閉じフェンスの表示オフセットは `0`。その `SourceMap` は文書範囲 `[8, 12)` 全体を隠し区間にしている。  
   根拠：`crates/presentation/src/projection/mod.rs:2607`
3. `Bias::After` による隠し区間の逆変換は、その区間の末尾 `12` を返す。  
   根拠：`crates/presentation/src/source_map.rs:90`
4. `VerticalMove::To(SourceOffset(12))` が成功として適用される。移動先が現在位置と同じでもフォールバックしない。  
   根拠：`crates/ui/src/view.rs:4118`、`:4142`

したがって、**非表示の閉じフェンスを移動先に選び、その逆変換が元の次行先頭を返すため、何度↑を押しても同じ位置になる。**

次行先頭のキャレットが直前のフェンスを開示しないことは、行ごとに所有権を判定する `range_disclosure` の経路とも整合する。根拠：`crates/ui/src/line.rs:49`、`:544`。

### ←で移動できる理由

←は表示行や `SourceMap` を介さず、前の書記素境界へ移動する。行頭からは前の物理行の本文末尾へ移るため、この例では閉じフェンスの改行直前、オフセット `11` に到着する。

そこでフェンス行が開示され、編集可能になる。

根拠：`crates/editor/src/movement.rs:33`、`:70`、`crates/editor/src/lib.rs:281`。

## (b) 期待挙動・受入条件

### 採用する移動規則

**↑↓は、現在の開示状態で表示される隣の行へ移動する。非表示・高さ0のフェンス行は飛ばす。**

フェンス行にはキャレットを置ける。左右移動などでフェンス内へ入った場合は、その行を開示し、↑↓の移動元として扱う。選択やIMEによって既に開示されているフェンス行は、移動先にもなれる。

非表示フェンスへ↑↓で入るために、先回りして開示する処理は追加しない。これは既存の表示行ベースの移動と、表の非表示区切り行を飛ばす扱いに合わせる設計判断である。

### 基本例

以下は折り返しが発生しない幅を前提とする。位置は「行番号、0始まりのカラム」で表す。

````text
1: before
2: ```
3: abc
4: ```
5:
6: after
````

フェンスが非開示の場合：

| 開始位置 | 操作 | 期待位置 |
|---|---|---|
| `(5, 0)` | ↑ | `(3, 0)` |
| `(3, 0)` | ↓ | `(5, 0)` |
| `(1, 0)` | ↓ | `(3, 0)` |
| `(3, 0)` | ↑ | `(1, 0)` |
| `(6, 0)` | ↑ | `(5, 0)`。実在する空行は飛ばさない |

閉じフェンス後の行に本文がある場合も、↑は最後のコード表示行へ移る。コード本文が折り返されていれば、その最後の折り返し行が対象となる。

### フェンス自体にキャレットがある場合

上の文書で、単独キャレットにより対象フェンスだけが開示された場合：

| 開始位置 | 操作 | 期待位置 |
|---|---|---|
| 閉じフェンス `(4, 1)` | ↑ | コード `(3, 1)` |
| 閉じフェンス `(4, 1)` | ↓ | 空行 `(5, 0)`。目標Xは保持 |
| 開きフェンス `(2, 1)` | ↑ | 前行の同じ表示Xに最も近い位置 |
| 開きフェンス `(2, 1)` | ↓ | コード `(3, 1)` |

フェンス行内の有効なカラムは、生の物理行の行頭から改行直前まで。開きフェンスでは言語指定や空白も含めて編集できる。到着位置は既存のshaper・文書境界規則に従い、短い行では行末にクランプする。連続した↑↓では元の目標Xを保持する。

ASCIIの同一フォントなら同じカラムになるが、異なるフォント・インデントをまたぐ場合は、文字数ではなく表示Xを基準とする。

### 空のコードブロック・文書端

- 開閉フェンスだけの空ブロックは、両方が非表示なら↑↓で飛ばす。
- コード本文に空行が1行ある場合、その空行は通常のコード表示行として停止先にする。
- 文書先頭・末尾方向に移動可能な表示行がなければ停止する。
- Shift+↑↓も同じ停止先を使い、anchorを保持してactiveのみを動かす。選択範囲には飛ばしたフェンスの文書バイトも含まれる。
- 移動後の開示・再レイアウトで、適用済みの文書位置を勝手に別位置へ変更しない。

## (c) 実装方針

修正対象は、表示行の移動先選択と、それを支える部分レイアウトの探索とする。

| 層・ファイル | 修正の要点 |
|---|---|
| `crates/presentation/src/layout.rs` | `vertical_target` が高さ0の構造行を飛ばし、方向側の次の表示行を選ぶ。表セル内の断片移動は維持する |
| `crates/ui/src/view.rs` | `layout_around`、`neighbor_block_window`、`target_in_neighbor` を調整し、非表示フェンスの向こうの表示行を取得する |
| 同上 | 部分レイアウトの端、ブロックの端、文書の端を区別し、候補が未取得という理由だけで文書端扱いにしない |

具体的には次を満たす。

1. **高さ0の行を移動候補から除外する。**  
   既存の文書位置対応や高さ計算への影響を抑えるため、まずは `LayoutLine` 自体を削除せず、移動候補の選択で除外する。
2. **隣接ブロックの物理1行だけでは探索を終えない。**  
   端が非表示フェンスなら表示行まで窓を進め、表示行のない空ブロックなら次のブロックへ進む。
3. **部分窓を必要な方向へ補う。**  
   現在の前後1行が高さ0の行だけになる場合にも、実在する次の表示行を取得できるようにする。
4. **既存の正式な投影情報を使う。**  
   フェンスらしい文字列をUIで独自判定しない。大きなブロックの全体表示・全体shapeも要求しない。
5. **文書端と解決失敗を区別する。**  
   隣接行が存在しない場合と、レイアウト取得・位置解決に失敗した場合を同じ成功結果に潰さない。既存の `None` によるフォールバック契約を保持する。

`SourceMap` 全体の `Bias::After` を反転する修正は採用しない。インラインマークアップ等の境界動作まで変わり、非表示フェンスを移動先に選ぶ問題も残る。

エディタコアの書記素移動と `move_vertical_to` は、現時点では変更不要とする。

## (d) 影響範囲と回帰リスク

| 領域 | リスク・維持する契約 |
|---|---|
| 見出し | 行高・文字サイズが異なっても、隣の表示行と目標Xを維持する |
| リスト・引用 | インデント、ぶら下げ、マーカー開示を含む表示座標を維持する。内包されたフェンスも確認する |
| 表 | 非表示区切り行のスキップ、セル内折り返し、ブロック後の実在する空行を維持する |
| 折り返し | 1回の↑↓で隣の表示行へ進む。物理行単位の移動へ退行させない |
| 文書端 | 非表示フェンスしか残っていない場合に、範囲外位置や循環探索を発生させない |
| 選択・IME | 開示状態と高さが変わっても、anchor・activeと文書位置の正しさを保つ |
| キャッシュ | 描画済みキャッシュの有無、正式indexの到着前後で停止先が変わらない |
| PageUp / PageDown | 同じステップ処理を反復するため、途中停止や移動距離の誤計算を確認する |
| Mermaid等の図 | 図専用の表示行を維持し、高さ0のソース行を飛ばす処理が図本体まで除外しない |

Page移動は `step_vertical_by_layout` を共用し、位置が変わらないと反復を終了する。今回の問題はPage移動の途中停止にも波及し得る。根拠：`crates/ui/src/view.rs:4151`、`:4174`。

キャレットの誤位置、移動不能、選択による誤編集につながる不整合は、エディタコアの品質基準により **merge blocker** とする。単に「↑で何か動く」だけでは受入としない。

## (f) 未確定事項

原因の静的な処理経路に未確定事項はない。実行による再現確認と修正後の検証は未実施。

期待挙動は本ドラフトで「非表示フェンスは↑↓で飛ばす」と定義した。これはオーナー原文で明示された仕様ではなく、既存の表示行ベースの移動契約に合わせた設計案である。

また、本ドラフト作成時点では Jev 判断は未取得だったが、その後 Commander が Jev で確認した（2026-11-15）: 方針は「↑↓の移動先選択でのみ非表示フェンスを飛ばす（SourceMap は変えない）」を確率 1.0 で採用。SourceMap の意味論変更と wontfix は棄却された。
