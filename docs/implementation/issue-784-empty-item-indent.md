# Issue #784 実装設計: 空の項目の Tab 入れ子で親が H2 化する問題

状態: 設計のみ。未実装・未検証。実装は AADW の実装ワーカーが行う。

## 問題

文書 `- abc\n- ` の2行目の空の項目で Tab を押すと、`plan_list_edit` の Indent は
`- abc\n  - ` への置換を返すが、CommonMark の「空の項目は段落を中断できない」
規則により、再パースではその `- ` の行が setext 見出し（H2）の下線として消費され、
親項目の段落「abc」が H2 として描かれる。再パースで項目自体が消えるため、
その後の Enter / Shift-Tab など項目前提の編集も壊れる。番号付きでは見出しに
ならない代わりに、番号が親の段落の継続テキストへ取り込まれて項目が消える。

実測した境界（パースで確認済み）:

- `- abc\n  - x`（非空）: 正常な入れ子。
- `- abc\n\n  - `（空行あり）: 正常な入れ子（ルーズリスト）。
- `- abc\n  - x\n  - `（既存の子リストの2番目以降の空項目）: 正常。
- `- [ ] abc\n  - `（タスク項目が親）: H2 化する。
- `1. abc\n   1. `（番号付きの空項目）: 番号が段落に取り込まれ項目が消える。
- `- abc\n  def\n  - `（親の本文が複数行）: 両行が見出しになる。

## 採択した方針（設計: Codex GPT-6.2 Sol、意味判断: Jev `noop_after_reparse` confidence 1.0）

（a）を採用する。Tab の置換候補を現行パーサーで検証し、移動先で項目が成立しない
場合は `Handled(NoOp)` を返す。`- abc\n- ` では Tab を押しても原文とキャレットが
そのまま残る。先に本文を入力してから Tab を押せば通常どおり入れ子にできる。
空行がすでにある場合や、既存の子リストに空項目を追加できる場合も従来どおり移動する。

（b）空行挿入でルーズな入れ子にする案は、Tab がインデント以外の変更（空行挿入と
リスト全体の表示間隔の変化）を持ち込むため不採用。（c）プレースホルダー文字案は
保存される原文に余分な内容を足すため不採用。パーサー側の特例扱いは CommonMark
からの逸脱になるため採らない。

## 検出方法と変更箇所

変更は `crates/markdown/src/list_editing.rs` の `plan_list_edit` の `Indent` 分岐に
置く。既存の前兄弟・インデント幅の判定を通過したら、`plan_ordered_move` または
`transform_subtree` で置換候補を作り、両経路を共通の検証に通す。番号付き項目は、
実際に適用される振り直し後の文字列で判定する。

1. **再パースの対象を絞る。** 開始行のリストマーカー直後から物理行末までが
   ASCII の空白・タブだけ、またはゼロバイトの項目を対象にする。`body_range` は
   タスク記号も除外するため、その空判定だけでは `[ ]` 付きの項目まで拾ってしまう。
   また、開始行が空でも後続ブロックを持つことがあるため、候補には後続行も含める。
2. **現在のブロックに置換候補を適用して一度だけパースする。**
   `ListEditProjection::source_range` を使い、前の兄弟、既存の空行や子リスト、
   対象より後ろの行を含むブロックを維持する。置換後のバイト長に合わせた範囲を
   既存の `parse_document` に渡す。入力時点のブロックを使うのは、Enter 直後の
   Tab もバックグラウンド解析を待たず処理する現行経路に合わせるため。
3. **移動した項目と直親を確認する。** 置換後のマーカー開始バイトに対応する
   正式な `ListItem` を `list_item_markers` で引き、所属する `List` の親が、
   元の前兄弟のマーカー位置に対応する `ListItem` であることを確認する。
   キャレット位置から検索すると、項目が消えた場合に親を拾うことがある。
   編集用射影の字句回復は、パーサーが認識しなかったマーカーを補うため、
   成功の根拠には使わない。
4. **検証結果を既存の編集契約で返す。** 項目と直親を確認できれば、元の
   `Replace` と `selection_after` を返す。確認できなければ、元の選択を持つ
   `Handled(NoOp)` を返す。UI はこの結果で Tab を消費し、バッファを
   書き換えず、undo 履歴にも追加しない。

「前の兄弟の末尾が段落で、空行も子リストもない」という条件は再現例の説明には
使えるが、適用判定には置かない。タイトリストでは `Paragraph` イベントが省略され、
子リストが存在しても末尾の別ブロックやマーカー種別によってはそこへ追加できない。
開始行の字句条件で追加パースの回数を抑え、成否は実際の置換結果から判定する。
同期パースのコストは対象ブロックの大きさに依存する。

## 回帰検証

| ケース | 確認する結果 |
|---|---|
| `- abc\n- `、タスク親、複数行の親、番号付きの空項目 | `Handled(NoOp)`。原文とキャレットが一致し、親の H2 化や番号マーカーの段落への取り込みが起きない |
| `- abc\n\n- `、`- abc\n  - x\n- ` | `Replace`。適用後の正式な木で、空項目が `abc` の直下に残る |
| `1. abc\n   1. x\n2. ` | `Replace`。空項目が子リストの `2.` になり、再パース後も正式な項目として残る |
| 非空項目、Unicode 空白だけの本文、タスク記号付き項目 | 空マーカー行の検証対象に入らず、既存の移動計画を維持する |
| マーカー直後がタブ、CRLF、文書途中のブロック | 空判定、改行の保持、バイト位置での項目照合が正しい |

- `hane-markdown` のテストで、置換文字列に加えて再パース後の親子関係を検証する。
  #765 の番号振り直しを含む既存テストがすべて通ること。
- GPUI の実キー経路のテストで、再現例で Tab を押しても選択・文書が変わらない
  ことと、移動できる空項目では直後の Enter と Shift-Tab が項目として効くこと。
- GUI 確認（司令塔）: macOS の開発ビルドで再現手順を通し、`abc` が通常の本文の
  大きさ・太さで表示されることを確認する。
- 性能の確認（司令塔）: 長い単一リストでも Tab の応答が実用範囲にあること。
